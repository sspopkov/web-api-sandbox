# Песочница браузерных API

Учебный frontend-проект для практического изучения современных браузерных API,
управления рендерингом и оптимизации производительности интерфейсов.

Проект состоит из небольших интерактивных лабораторных работ на React и TypeScript.
Каждая лабораторная показывает проблему, наивный способ её решения, более эффективную
реализацию с Browser API и влияние выбранного подхода на UX и производительность.

## Цель проекта

Frontend-разработчику важно понимать не только React, но и работу самого браузера:
как он выполняет JavaScript, обрабатывает события, рассчитывает компоновку, рисует
кадры, планирует фоновые задачи и распределяет нагрузку в основном потоке.

В проекте можно:

- переключаться между наивной и оптимизированной реализациями;
- запускать сценарии, нагружающие основной поток;
- наблюдать простые диагностические метрики прямо в интерфейсе;
- сравнивать поведение реализаций в Chrome DevTools.

## Технологии

- TypeScript;
- React;
- Vite;
- современный CSS;
- ESLint;
- Prettier.

Проект намеренно не использует тяжёлые UI-библиотеки и абстракции, скрывающие
непосредственную работу браузерных API.

## Лабораторные работы

### ResizeObserver

- **Назначение:** отслеживает изменение размера конкретного элемента, а не всего окна.
- **Пример:** изменяемый виджет аналитики перестраивает содержимое в зависимости от
  собственной ширины.
- **Где полезно:** панели с изменяемым размером, редакторы, графики, адаптивные
  карточки и встраиваемые виджеты.
- **Эффект:** компонент точнее адаптируется к контейнеру и не зависит от глобального
  события `window.resize`.

### IntersectionObserver

- **Назначение:** определяет появление элементов в области видимости без ручной
  проверки их координат при каждом событии `scroll`.
- **Пример:** лабораторная отдельно показывает карточки, которые сейчас находятся
  во viewport, и карточки, уже прошедшие ленивую инициализацию. Служебный элемент
  подгружает следующую порцию списка.
- **Где полезно:** ленивая загрузка изображений, бесконечные ленты, аналитика показов
  и отложенная инициализация виджетов.
- **Эффект:** меньше срочных вычислений во время прокрутки и проще логика загрузки.
  Для честного сравнения оба режима используют одинаковый порог видимости, а панель
  диагностики показывает вызовы обработчиков и объём обработанной работы.

### Web Workers

- **Назначение:** выносят ресурсоёмкие вычисления из основного потока.
- **Пример:** подсчёт простых чисел выполняется либо в основном потоке, либо внутри
  Web Worker. Движущаяся точка наглядно показывает блокировку интерфейса.
- **Где полезно:** парсинг больших объёмов данных, сжатие, индексация, обработка
  изображений и сложные вычисления.
- **Эффект:** интерфейс остаётся отзывчивым во время фоновых вычислений.

### requestIdleCallback

- **Назначение:** выполняет некритичные фоновые задачи в периоды простоя браузера.
- **Пример:** очередь коротких задач обрабатывается порциями; для браузеров без
  поддержки API предусмотрен запасной механизм через `setTimeout`.
- **Где полезно:** прогрев кеша, предварительные вычисления, некритичная аналитика
  и очистка после рендера.
- **Эффект:** уменьшает заметные задержки. API нельзя использовать для срочных или
  критически важных операций, поскольку время вызова не гарантируется.

### requestAnimationFrame

- **Назначение:** синхронизирует обновления анимации с отрисовкой кадров браузером.
- **Пример:** одна и та же анимация запускается через `setInterval` и
  `requestAnimationFrame`; интерфейс показывает число кадров и примерный FPS.
- **Где полезно:** анимации DOM, Canvas, WebGL и пользовательские переходы.
- **Эффект:** более плавное движение, экономия работы в невидимых вкладках и
  предсказуемая очистка через `cancelAnimationFrame`.

### Обработка событий

- **Назначение:** демонстрирует отдельные обработчики, делегирование, всплытие,
  перехват, `preventDefault` и `stopPropagation`.
- **Пример:** список из 60 кнопок переключается между отдельными обработчиками и
  одним обработчиком контейнера. Журнал показывает порядок прохождения событий.
- **Где полезно:** таблицы, меню, деревья и большие динамические списки.
- **Эффект:** делегирование сокращает число обработчиков и упрощает работу с
  динамически добавляемыми элементами.

### Пассивные обработчики событий

- **Назначение:** показывают, как `{ passive: true }` сообщает браузеру, что
  обработчик не будет отменять прокрутку.
- **Пример:** прокручиваемый блок сравнивает пассивный обработчик `wheel` с
  блокирующим обработчиком, вызывающим `preventDefault`.
- **Где полезно:** сбор метрик прокрутки и обработка `wheel`, `touchstart` и
  `touchmove`, если отмена события не требуется.
- **Эффект:** браузер может начинать прокрутку, не ожидая выполнения JavaScript.

### MutationObserver

- **Назначение:** наблюдает за изменениями DOM без постоянного опроса дерева.
- **Пример:** DOM-песочница напрямую добавляет и удаляет верхние и вложенные узлы,
  меняет атрибуты цели и потомков и обновляет содержимое Text-узла. Конфигурация
  позволяет отдельно исследовать `childList`, `attributes`, `characterData` и
  область действия `subtree`.
- **Где полезно:** плагины редакторов, сторонние встраиваемые блоки, аналитика и
  интеграция с кодом, изменяющим DOM напрямую.
- **Эффект:** предоставляет сгруппированные и точные записи об изменениях DOM.
  Невалидная конфигурация без выбранного типа мутаций безопасно приостанавливает
  observer и объясняет ограничение `MutationObserverInit`.

### Performance API

- **Назначение:** измеряет операции с высокой точностью и создаёт именованные
  временные метки и измерения.
- **Пример:** сортировка массива измеряется через `performance.now()`,
  `performance.mark()`, `performance.measure()` и `PerformanceObserver`.
- **Где полезно:** профилирование пользовательских сценариев, запуска приложения
  и дорогих операций.
- **Эффект:** метрики можно сопоставить с записью производительности в DevTools.

### Производительность рендеринга

- **Назначение:** показывает влияние JavaScript и DOM-операций на основной поток и
  конвейер рендеринга.
- **Пример:** лабораторная демонстрирует долгую задачу, частые обновления DOM,
  чередование чтений и записей layout и их пакетную обработку.
- **Где полезно:** панели мониторинга, редакторы, большие таблицы, инструменты
  перетаскивания и интерфейсы со сложной анимацией.
- **Эффект:** группировка чтений и записей DOM уменьшает число принудительных
  перерасчётов компоновки и освобождает основной поток.

## Структура проекта

```text
src/
  app/
  components/
  labs/
    resize-observer/
    intersection-observer/
    web-workers/
    request-idle-callback/
    request-animation-frame/
    events/
    passive-listeners/
    mutation-observer/
    performance/
    rendering/
  utils/
  workers/
```

Логика каждой лабораторной расположена рядом с соответствующим компонентом. Общие
компоненты отвечают только за информационные блоки, метрики и переключатели режимов.
Наблюдатели, обработчики событий, таймеры, кадры анимации и веб-воркеры корректно
освобождаются в функциях очистки React.

## Локальный запуск

```bash
npm install
npm run dev
npm run build
npm run lint
```

После запуска откройте адрес, который выведет Vite. Обычно это:

```text
http://127.0.0.1:5173/
```

## Работа с Browser DevTools

Откройте **Chrome DevTools -> Performance** и запишите профиль во время выполнения
лабораторных. Особенно полезно сравнивать наивный и оптимизированный режимы.

Обратите внимание на:

- загрузку основного потока (**Main thread**);
- долгие задачи (**Long tasks**);
- выполнение JavaScript (**Scripting**);
- расчёт компоновки (**Layout**);
- рендеринг и отрисовку (**Rendering** и **Painting**);
- частоту кадров (**FPS**).

Встроенная диагностика намеренно остаётся простой: она помогает быстро увидеть
разницу, а DevTools предоставляет подробную временную шкалу работы браузера.
